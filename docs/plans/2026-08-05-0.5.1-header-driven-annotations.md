# massbank 0.5.1 — header-driven annotation parsing

Supersedes the scoping in `2026-08-02-header-driven-annotation-parsing.md` (that document's defect
analysis stands; its open questions are answered below and its 0.5.1-vs-0.6.0 hedge is dropped).

**One release, one `fix:`, 0.5.1.** The package has **0 dependents on npm** (verified via the
registry dependents search) and NoBS is the only consumer. `BuildErrorCode` shipped 2026-08-03, two
days before this plan. Splitting the type removals into a separate minor would be ceremony

## The defect, measured

`AnnotationTableParser.parse` captures the header into `record._PK$ANNOTATION_HEADER`
(`table-parsers.ts:126`) and then **never consults it**. `parseAnnotationLine` is private, receives
no header, and branches on `parts.length` alone. Its own comment at `:175` says _"The header tells
us the format, so we parse accordingly"_ — the code does not.

**There is no branch for five tokens.** Read `:186-223`: `=== 4`, else `=== 3`, else _"2 parts"_.
A five-token line falls into the two-token fallback and sets `mz` and `annotation` only.

Five tokens is **100% of the real annotated corpus**:

```
50 / 50 annotated records:  PK$ANNOTATION: m/z tentative_formula formula_count mass error(ppm)
                              53.0389 C4H5+ 1 53.0386 6.47
```

Measured consequence — parse a corpus record, strip `_original`, re-serialise:

```
annotated records: 50
identical without _original: 0
differs: 50

   with _original:   53.0389 C4H5+ 1 53.0386 6.47
  without        :   53.0389 C4H5+
```

**Three of five columns are lost on every real annotated record.** `_original` is not a
formatting optimisation — it is the only thing preserving them, which is exactly why 0.5.0 had to
grow the preservation machinery and why that machinery took five review rounds.

### The second half of the asymmetry

`record-serializer.ts:132-148` writes annotation columns **by presence** (`if (ann.annotation)`,
`if (ann.exactMass !== undefined)`) under a header it prints verbatim. So the writer emits a
variable number of columns beneath a header that promises a fixed set. Reader and writer disagree
about the same table.

**Both sides must become header-driven.** Fixing only the parser moves the asymmetry rather than
removing it.

## The measured header vocabulary

Every distinct annotation header in the corpus and in this repo's own fixtures:

| header                                                | source                            |
| ----------------------------------------------------- | --------------------------------- |
| `m/z tentative_formula formula_count mass error(ppm)` | 50/50 corpus records              |
| `m/z annotation exact_mass error(ppm)`                | repo fixtures                     |
| `m/z ion`                                             | repo fixtures (docstring example) |
| `m/z`                                                 | repo fixtures (`reparse-check`)   |

That is the whole real-world set. The vocabulary below is derived from it, not invented:

| normalised token                        | maps to                                                                       |
| --------------------------------------- | ----------------------------------------------------------------------------- |
| `mz`                                    | `mz` (required; a row whose first column is not numeric is skipped, as today) |
| `annotation`, `tentativeformula`, `ion` | `annotation`                                                                  |
| `exactmass`, `mass`                     | `exactMass`                                                                   |
| `errorppm`, `error`, `ppm`              | `errorPpm`                                                                    |
| anything else (`formulacount`, …)       | `extra[<original token>]`                                                     |

**Normalisation:** lowercase, strip every non-alphanumeric. So `error(ppm)`, `error_ppm` and `ppm`
all collapse to `errorppm`. Matching literally means a vocabulary that grows forever.

**Do not extend this table by imagination.** A token that is not in the corpus and not in a fixture
belongs in `extra`, where it is preserved losslessly and costs nothing.

## Corrections from the review round (2026-08-06) — all measured

Four findings changed the design. Each was verified by running something, not by reading.

**C1 — `parseRecord` has no warning channel. BLOCKING as originally written.**
`parseRecord(text): MassBankRecord` is the whole signature, and `grep -rn "ValidationWarning|warnings" src/parser/` returns nothing. The original answer to open question 2 ("fall back AND emit a `ValidationWarning`") specified a behaviour the architecture cannot express.
**Fix:** warn at the **validation** layer, not the parse layer. `validateContent` already returns `{errors, warnings}` and already runs rules over the parsed record; a rule that checks `_PK$ANNOTATION_HEADER` against the vocabulary and warns when it does not map is the natural home. Parsing stays pure and the warning becomes independently testable.

**C2 — `_original` must stay, and so must two of the three guards. The original plan was internally inconsistent.**
`SerializationRule` compares **text**, not objects (`serialization-rule.ts:26-31`, `findFirstDifference(normalizedOriginal, serialized)`), so byte-exact round-trip is a hard requirement and any numeric reformatting is a _blocking_ validation error.
Measured: **4624 / 4624** numeric annotation tokens in the corpus survive `parseFloat` → `String` byte-identically, so the corpus is safe. But a value like `1.10`, `1.0` or `1e5` would not, and such a record exists somewhere.
**Fix:** keep `_original` on the mapped path too, as a **pure byte-fidelity optimisation** — not as the column-preservation mechanism it is today. `extra` solves the loss problem; `_original` solves the formatting problem; they are different jobs. Consequently `ANNOTATION_ORIGINAL_LINE_INJECTION` and `ANNOTATION_ORIGINAL_UNREADABLE` **must be kept** — they guard printing `_original` verbatim, and `_original` still gets printed. Deleting them while keeping `_original` was the plan contradicting itself.

**C3 — the middle-gap case is real, reachable by editing, and the existing guards already answer it.**
Measured: every corpus annotation row is exactly `hdr=5 row=5` (**1156 / 1156**) — no surplus rows, no short rows. So the "surplus tokens join the last column" rule is untested by real data and is a decision about hypothetical input, not a fix for observed input.
But a **middle** gap is reachable the moment a user edits: with header `m/z tentative_formula formula_count mass error(ppm)`, clearing `mass` while keeping `error(ppm)` and then emitting "nothing for absent, end the row" produces four tokens whose fourth is the _error_ value — which reparses as `mass`. That is precisely the bug class this release exists to remove, reintroduced in the fix.
**Fix:** the existing `ANNOTATION_ERROR_PPM_WITHOUT_EXACT_MASS` / `*_WITHOUT_ANNOTATION` guards **are** middle-gap guards, expressed in the old fixed column order. Generalise them rather than delete them: **a row may not populate column N+1 while column N is absent, for the record's actual header order.** Do not invent a placeholder token for an absent middle column — MassBank has no documented convention for one and the corpus contains no example, so guessing would be fabrication.

**C4 — the Java reference defines no annotation column vocabulary.**
`MassBank-cli-tools` contains exactly one annotation header, in a test resource (`src/test/resources/recordfiles/MSBNK-test-TST00003.txt:33`: `m/z annotation exact_mass error(ppm)`, already in the table above), and no controlled list anywhere in its source. So there is no authoritative vocabulary to defer to, `tentative_formula`/`formula_count` are contributor convention rather than grammar, and the header space is genuinely open-ended. That is an argument **for** `extra` as the catch-all rather than for enumerating harder.

## Answers to the three open questions

**1. Unmapped columns → `extra: Record<string, string>` on `Annotation`,** keyed by the _original_
header token (not the normalised one) so the serializer can look up a column by the very name it is
about to print. This is what lets `_original` die: with every column addressable, rebuilding from
typed fields is lossless.

**2. Unknown headers → fall back to today's token-count heuristic; warn from the VALIDATION layer**
(see C1 — the parser cannot warn). Refusing would be more honest in the abstract and would break
every unknown-in-the-wild record on a patch release. The warning makes the imprecision visible
without breaking anyone.

**3. Case and punctuation → normalise** (question 3 above).

## Tasks

### Task 1 — `Annotation.extra`, and the column vocabulary

**Files:** `src/record.ts`, new `src/parser/annotation-columns.ts` + test.

- [ ] Add `extra?: Record<string, string>` to `Annotation`, documented as "columns the header names
      that have no typed field; keyed by the header token exactly as written".
- [ ] New module exporting `normaliseHeaderToken(token): string` and
      `mapAnnotationHeader(header: string): AnnotationColumn[]`, where `AnnotationColumn` is
      `{ token: string; field: 'mz'|'annotation'|'exactMass'|'errorPpm'|null }` — `null` meaning
      "goes to `extra` under `token`".
- [ ] `mapAnnotationHeader` returns `null` for a header it cannot use at all (no `m/z` column), so
      the caller can take the fallback path.
- [ ] **Test** the four real headers above, plus: mixed case, `error_ppm`, a header with a token
      that maps nowhere, and a header with no `m/z`.

### Task 2 — Header-driven `parseAnnotationLine`

**File:** `src/parser/table-parsers.ts`.

- [ ] Thread the mapped columns into `parseAnnotationLine` (it is private; change its signature).
- [ ] When the header maps: assign token _i_ to column _i_. Numeric fields (`exactMass`,
      `errorPpm`) parse with `Number.parseFloat` and are **omitted when NaN** rather than stored as
      NaN. Non-typed columns land in `extra`.
- [ ] A row with **more tokens than the header has columns**: surplus tokens join the last column's
      value space-separated — an annotation containing a space is likelier than a table with a
      wrong header. Cover it with a test either way.
- [ ] A row with **fewer** tokens: assign what is there, leave the rest absent.
- [ ] When the header does not map: today's `parts.length` heuristic verbatim, plus a
      `ValidationWarning` naming the header. **Keep `_original` on this path.**
- [ ] Stop setting `_original` on the mapped path.
- [ ] **Test:** the 5-column corpus row parses to `mz/annotation/extra.formula_count/exactMass/
    errorPpm` with the right values; the 4-column fixture row; `m/z ion`; and the unknown-header
      fallback still parses and warns.

### Task 3 — Header-driven serialization

**File:** `src/serializer/record-serializer.ts`.

- [ ] Emit one column **per header token, in header order**, reading typed fields and `extra`.
      A column with no value emits nothing and ends the row (trailing gaps are not padded).
- [ ] Keep the `_original` fast path for rows that still carry one (fallback-parsed records).
- [ ] Keep the existing default header when a record has none.
- [ ] **Test:** a record built by hand with `extra` round-trips through
      `serialize → parse → serialize` unchanged.

### Task 4 — Delete the workarounds

**Files:** `src/builder/build-record.ts`, `src/builder/exceptions.ts`.

Every one of these exists only because the parser dropped columns:

- [ ] `checkAnnotationDiscardedColumns` and both branches.
- [ ] `wasAnnotationRowEdited` and the all-or-nothing table rule — a row's `_original` is now
      per-row: used when present and unedited, dropped when edited, with no cross-row coupling,
      because dropping it no longer loses columns.
- [ ] The `looksNumeric` / `parseFloat` coupling and its regression lock.
- [ ] `ANNOTATION_DISCARDED_COLUMN` from `BuildErrorCode`.

**KEEP (corrected — C2):** `_original` itself, `reparseAnnotationOriginal`,
`ANNOTATION_ORIGINAL_LINE_INJECTION` and `ANNOTATION_ORIGINAL_UNREADABLE`. `_original` is still
printed verbatim for byte fidelity, so the guards protecting that print still have a job. Deleting
them while keeping `_original` would be removing a live guard.

- [ ] Their tests.

**Generalise, do not delete, the middle-gap guards (C3):**
`ANNOTATION_ERROR_PPM_WITHOUT_EXACT_MASS`, `ANNOTATION_ERROR_PPM_WITHOUT_ANNOTATION` and
`ANNOTATION_EXACT_MASS_WITHOUT_ANNOTATION` encode "no gap before a populated column" in the old
fixed order. Re-express them against the record's actual header order. Add a test for the editing
scenario in C3 — clear a middle column, keep a later one, and assert the build is rejected rather
than silently emitting a column-shifted row.

**Keep** the annotation shape guards that are still real: `ANNOTATION_NOT_FINITE`,
`ANNOTATION_EXACT_MASS_WITHOUT_ANNOTATION`, `ANNOTATION_ERROR_PPM_WITHOUT_ANNOTATION`,
`ANNOTATION_ERROR_PPM_WITHOUT_EXACT_MASS`, `ANNOTATION_TEXT_LOOKS_NUMERIC`,
`ANNOTATION_TEXT_NOT_ROUND_TRIPPABLE` — **but re-derive each against the new parser before keeping
it.** Several were shaped by the token-count reader; a guard that guarded a now-impossible failure
must go, and one that still fires must have a test proving it.

- [ ] For each retained code: delete the guard, confirm a test goes RED, restore. A guard that
      cannot be made to fire is dead and should be deleted with the rest.

### Task 5 — The corpus is the gate

- [ ] **Semantic round-trip, all 50 annotated records:** parse → strip every `_original` → serialize
      → parse again, and assert the **objects** match field-for-field including `extra`. This is the
      test that would have caught the current defect; text comparison would not, because
      `serialize(parse(x)) === x` is invariant under any consistent relabeling of columns.
- [ ] **Text round-trip, all 112:** `serialize(parse(x)) === x`. Numeric reformatting is the risk
      here (`1.10` → `1.1`); if it bites, that is a finding to report, not to paper over with
      `_original`.
- [ ] `buildRecord(parseRecord(file))` succeeds on all 112 **without** the preservation machinery.
- [ ] Editing one annotation row and rebuilding preserves every other row's columns — the scenario
      that is impossible today.

## After it ships

NoBS's `^0.5.0` picks up 0.5.1 automatically, but both lockfiles must be refreshed in one commit.
Then **edit-an-uploaded-record** is unblocked: with `extra`, parsing a third-party record into
`MassBankRecordShape` and rebuilding it is lossless, so the NoBS-side guard reduces to carrying
`PK$ANNOTATION` through the draft type and making the accession mint conditional on there being no
existing accession.

**Two NoBS-side facts measured now, so the follow-up does not rediscover them:**

- `canonicalise` (`recordMerge.ts`) **does preserve a nested `extra` object**. Verified by running
  `finalizeRecord` with annotation rows carrying `extra`: both rows survived with
  `extra: {"formula_count":"1"}` intact. `Array.isArray` → `.map` passes non-strings through
  untouched, so annotation arrays are safe.
- **But `canonicalise` does NOT trim strings nested inside objects in an array.** The same run
  returned `annotation: " C3H4N+ "` with its padding intact. `canonicalise` trims top-level strings
  and string _elements_ of arrays; it does not recurse into row objects. So once annotations are
  editable, a user leaving a trailing space in an annotation would reach `buildRecord` untrimmed and
  hit `ANNOTATION_TEXT_NOT_ROUND_TRIPPABLE` — a build failure `canonicalise` exists to prevent.
  Fix belongs in the edit-uploaded-record work, not here: extend `canonicalise` to trim string
  properties one level into array-of-object fields, with a test asserting a padded annotation
  builds cleanly.
